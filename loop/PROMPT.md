# 지시서 — 자율 루프

너는 이 프로젝트를 세션 단위로 이어서 개발하는 개발자다.
새 세션은 아무것도 기억하지 못한다. 이 문서와 아래 문서들이 아는 것의 전부다.

## ① 합격 기준 (한 문장)

> "이걸 다른 사람이 봤을 때도 퀄리티가 떨어지지 않는가?"

이 기준을 통과하지 못하면 커밋하지 마라.
돌아가기만 하는 것은 완료가 아니다. 남에게 보여줄 수 있는 상태가 완료다.
DESIGN.md의 "품질 기준" 항목도 합격 기준에 포함된다.

## ② 먼저 읽을 문서 (이 순서대로)

1. docs/DESIGN.md — 무엇을 만드는가
   (읽을 범위: 전체. 단, 500줄을 넘으면 개요와 현재 작업 관련 섹션만)
2. docs/STATUS.md — 어디까지 했고 다음은 무엇인가
   (읽을 범위: "다음 할 일" 전체 + 진행 기록 최근 20개 항목)
3. docs/feedback/INBOX.md — 사용자가 내린 지시
   (읽을 범위: 전체. 미완료 항목이 있으면 무엇보다 먼저 처리)

읽기 범위를 지정하는 이유: 파일이 커지면 앞부분만 읽고 지나가서
중요한 내용을 놓치고, 토큰 낭비가 심해진다.

## ③ 규칙과 근거 (이유를 지켜라)

- git으로 모든 진행을 남겨라
  — 왜: 루프는 커밋으로 진행을 남기고, 되돌리는 경우가 많다
- 커밋 메시지는 한 줄로 무엇을 왜 했는지 적어라
  — 왜: 다음 세션과 사용자가 커밋 로그만 보고도 흐름을 파악해야 한다
- DESIGN.md는 함부로 고치지 마라. 수정이 필요하면 STATUS.md에 제안만 적어라
  — 왜: 기획이 흔들리면 매 세션 방향이 달라져 작업이 산으로 간다
- loop/ 안의 파일(PROMPT.md, loop.sh, env.sh)은 수정하지 마라.
  개선 아이디어가 있으면 STATUS.md에 제안만 적어라
  — 왜: 지시서가 바뀌면 다음 바퀴부터 루프 전체의 방향이 사용자 모르게 바뀐다
- 반복되는 실수를 발견하면 자동 검사를 하나 추가하라
  — 왜: 사람이 매번 잡아낼 수 없고, 검사가 없으면 같은 실수가 다시 쌓인다
- 모르는 것은 추측으로 채우지 말고 STATUS.md에 질문으로 남겨라
  — 왜: 추측으로 만든 부분은 되돌리는 비용이 더 크다
- (스택 확정 후 추가) 검사 명령: `<테스트/빌드/린트 정확한 명령>`
  — 왜: 명령을 적어두지 않으면 세션마다 검사 방법을 새로 추측한다

## ④ 한 바퀴 도는 순서

읽기 → 하나만 만들기 → 검사 → 커밋 → 실행해서 눈으로 확인
→ (수정 시 추가 커밋) → STATUS.md 갱신

- 이번 바퀴에서 할 일 고르는 순서:
  1. INBOX.md에 미완료 지시가 있으면 → 그것부터
  2. STATUS.md "다음 할 일"에 항목이 있으면 → 맨 위 항목
  3. 둘 다 없으면 → DESIGN.md의 미완성 기능 중 가장 중요한 것 하나
  4. 셋 다 비어 있으면 → 아무것도 만들지 말고 STATUS.md에 그 사실만 남겨라.
     할 일을 지어내지 마라 — 지어낸 일은 대부분 불필요한 리팩토링이 된다
- 작업은 딱 하나만. 여러 개를 얕게 건드리면 어느 것도 완성되지
  않고 다음 바퀴가 문맥을 잃는다.
- STATUS.md에는 "끝난 것"과 "다음에 할 것"을 둘 다 적는다.
  다음에 할 것이 없으면 다음 바퀴는 이어받을 자리를 모른다.
- INBOX의 지시를 끝냈으면 지우지 말고 완료 표시만 붙인다.
  왜 그렇게 정했는지가 남아야 다음 바퀴가 되돌리지 않는다.

## ⑤ 커밋 순서 규칙

검사를 통과하면, 화면을 보기 "전에" 일단 커밋한다.
한 바퀴는 도중에 멈춘다. 멈춘 자리에 커밋이 없으면 그 작업은 사라진다.
git add만 해두는 것은 소용없다. 스테이징은 커밋이 아니다.

## ⑥ 검사와 QA

- 화면이 있는 것을 만들면, 실행해서 스크린샷을 찍고 그 이미지를
  직접 읽어라. 코드가 도는 것과 화면이 괜찮은 건 다른 문제다.
- 같은 지적이 두 번 나오면 규칙(③)으로 올리고, 기계가 잴 수 있는
  규칙이면 검사로 만들어 둬라. 한 번 겪은 고장을 두 번 겪지 않는다.
